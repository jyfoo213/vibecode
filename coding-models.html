AI CLOUD BASICS / 6 MIN READ

Local vibe coding vs
cloud vibe coding.

Same idea-to-website journey. A different place to do the work.

Think in three places: the workbench where you build, the repository where you save and review, and the live site your users visit.

01 / WORKBENCH

Develop & preview

Your laptop or a cloud workspace. Edit files, run tests, and try the app.

01 / WHERE THE WORK HAPPENS

Two workbenches. One publishing path.

The assistant’s model can run remotely in either workflow. “Local” here describes your project files, terminal, tests, and preview server—not necessarily the AI model.

Cold start: both workflows need a working toolchain. A fresh cloud workspace may also need to be provisioned.

02 / WHAT YOU’RE FEELING IS THE STARTUP TAX

Cold starts cost time.
Warm loops tell a different story.

Session time=startup / resume+number of edits × iteration time

An already configured laptop often gets you to the first edit faster than a fresh cloud workspace. Once a cloud workspace is running, it can also reuse its files, dependencies, and processes. Per-edit speed then depends on compute, model response time, build time, network latency, and the size of the task.

Why did this session have setup work again?

The attached environment began in a “starting” state. The repository was already present; I inspected its runtime, checked sources, restarted a preview server, and launched browser checks. I did not reinstall a framework or recreate the repository. Some of that work was validation of an unfamiliar project; some was restarting processes. Those costs can occur locally too, though an always-ready laptop often hides them.

A sleeping workspace is different from a deleted workspace. Sleep may preserve the disk but stop processes. Deletion or replacement may require rebuilding from the repository. Persistence and retention depend on the provider; this diagram does not promise Codex-specific retention behavior.

Can cloud setup become as repeatable as local setup?

Often. Pin the runtime, keep a lockfile, document a one-command setup, cache dependencies, and reuse a workspace when supported. Prebuilt environment images move setup work before the session starts. They can improve startup time while adding maintenance, storage, and potentially compute costs. GitHub Codespaces documents prebuilds as one example; it is not the service running this session.

Is localhost always on my laptop?

No. “Localhost” means the machine where a process is running. In a cloud terminal, localhost points to that remote environment. A forwarded preview URL lets your browser reach the remote server. Neither preview is the production site.

03 / CHOOSE FOR YOUR WORKING STYLE

The trade-offs, without the hype.

Typical trade-offs; actual speed, cost, and persistence depend on the setup.
DecisionLocal workbenchCloud workbench

A practical starting point: keep your comfortable local loop for frequent hands-on work. Use a cloud workspace when access, isolation, or remote capacity helps. Keep GitHub and automated checks as the shared handoff so you can switch.

04 / HOW THIS CONNECTS TO AI CLOUD DEPLOYMENT

Three independent choices.

01

Where do I build?

Laptop or remote workspace. This determines the development experience.

02

Where does the app run?

GitHub Pages, a hosted server, or another runtime. This determines how users access the product.

03

Where does the AI run?

A hosted model API or self-hosted inference. This determines inference latency, cost, data flow, and operational responsibility.

IF AI ATLAS LATER BECOMES AN AI-POWERED APP

User’s browser → App backend → Model API / inference service

The backend would protect API credentials, enforce budgets, and handle requests. GitHub Pages serves static files; it does not run that backend. Today AI Atlas needs no model API at runtime: its lessons and calculator run in the browser.

The reason to move a service to the cloud is usually shared access, managed operations, or elastic capacity. That does not require every developer’s workbench to move there. A locally developed product can be entirely cloud-hosted.

05 / THIS WEBSITE, AS A CONCRETE EXAMPLE

What happened in this session?

  1. Resume the remote workbench. Wait for the attached cloud environment; inspect the existing checkout.
  2. Build and preview remotely. Edit static files, run tests, and check desktop/mobile layouts in a browser.
  3. Save the code to GitHub. The first hub release went directly to main. This topic follows a feature branch → pull request → merge path.
  4. Publish from committed code. GitHub Actions tests and builds the static files, then deploys them to GitHub Pages.
  5. Serve readers independently. The published site can stay available when the development workspace sleeps.
Try this as a PM: find the actual bottleneck

For the next three sessions, measure time to first successful preview, median edit-to-preview time, and time from merge to live site. Separate model waiting from build time and workspace startup. Decide whether a warm workspace, a prebuild, or local development would remove the biggest delay. Avoid universal “cloud is slower” claims from one cold start.
