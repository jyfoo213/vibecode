YOUR QUESTION / A SYSTEMS DESIGN WALKTHROUGH

Inside
AI Atlas.

A static website with interactive behavior. The browser does the work; GitHub Pages delivers the files.

Today: HTML + CSS + JavaScript + JSON. No production application server, shared database, sign-in, or runtime model API.

01 / WHAT HAPPENS WHEN I OPEN THE SITE?

Files arrive. The browser runs them.

  1. Your browser requests a page from jyfoo213.github.io/vibecode/.
  2. GitHub Pages returns its static HTML and linked assets.
  3. JavaScript reads the relevant public JSON dataset—for example, questions or landscape profiles.
  4. The page renders interactive views and reads this browser’s saved preferences.
  5. Your actions change the view. Personal state is saved locally; the public JSON is not edited.
What exactly does the frontend do?

HTML gives the page structure, CSS controls its appearance and responsive layout, and JavaScript handles behavior. The frontend can search, filter, compare players and calculate costs without contacting an AI model. Some guide content is already present in HTML; scripts enhance it with interactive controls.

Is the JSON dataset a database?

It is a versioned collection of public content files, not a shared database service. An agent edits those files in the repository, then tests and deploys an update. Marking a question done does not write into that public dataset.

03 / THE LANGUAGES AND TOOLS

Small pieces with clear jobs.

The current repository uses browser standards rather than a frontend framework.

Why no React or database yet? This product currently delivers learning content and browser-local interactions. Native HTML and small JavaScript modules meet that need with fewer moving parts. A larger framework or backend becomes useful when it solves a concrete new job—not simply because the site has more pages.

04 / TRACE ONE ACTION: “MARK DONE”

Completion stays with this browser.

  1. Click: you mark a question done.
  2. Update state: JavaScript sets that question’s lifecycle to done, preserving its notes and verdict.
  3. Save locally: the state is written to localStorage.
  4. Render again: active lists omit done/archived questions; the archive can still show them.
  5. Return later: this browser reads the saved state. Restore or Undo can bring the question back.

No database request or GitHub commit happens in this flow. Clearing site data or changing browser/device can lose that local state; exported JSON provides a backup. If browser storage is unavailable, changes may last only until you leave the page.

Where is the backend?

There is no production application backend in this version. GitHub Pages has infrastructure that serves files, but it does not run our Node.js preview server or execute a database API for us. The cloud coding workspace is a development environment, not the site’s live application server.

05 / IF CROSS-DEVICE SYNC BECOMES IMPORTANT

Add a backend for a real need.

Browser → Sign-in + authorised API → Shared database

A future backend could store private state by user and question ID. It must enforce who can read/write each record, handle failures and sync conflicts, and keep server secrets out of the frontend. The public learning content can still stay on GitHub Pages.

You chose browser-local storage with no sign-in for now. No database provider, paid service or authentication system has been provisioned. This diagram shows a possible extension, not the current implementation.
